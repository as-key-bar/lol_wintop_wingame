## Project

`wintop-wingame` is a desktop-first web guide for League of Legends top-lane matchups. Phase 1 lets users choose their champion and the opponent, then access verified matchup replays. The tool does not control the game client or automate gameplay.

## Current implementation

- Frontend: Next.js, TypeScript, React, under `frontend/`.
- Backend: FastAPI under `backend/`; launch with `--app-dir backend/src`.
- Champion catalog: `backend/src/app/data/champions.json`, generated from Riot Data Dragon; current version is 16.22.1.
- Catalog updater: `python3 scripts/update_champion_catalog.py`.
- Champion endpoint: `GET /api/v1/champions?q=<query>`.
- Search supports Japanese and English names, generated romanized Japanese, case-insensitive partial matching, punctuation/long-vowel normalization, and `b`/`v` equivalence.
- Matchup catalog & DB persistence: `backend/src/app/data/matchups.json` ships empty on purpose (no third-party channel data is bundled; `python3 scripts/update_matchup_catalog.py --playlist <url>` can fill it locally). Videos enter the DB through the search-and-upvote flow, and the seed file, when filled, seeds MySQL (`matchup_videos` and `matchup_video_votes` in `backend/src/app/database.py` / `database/schema.sql`, with automatic JSON fallback when DB is unreachable).
- Matchup & Upvote endpoints: `GET /api/v1/matchups/{playerChampionId}/{opponentChampionId}` returns saved `verified` videos sorted by `upvoteCount` desc > `gamePatch` desc > rank tier desc, followed by YouTube search results (`backend/src/app/youtube_search.py`, cached 72 hours), at most 8 in total. **Saved videos no longer suppress the search** (provisional policy, DEC-019; expect it to change with use). `POST /api/v1/matchups/{playerChampionId}/{opponentChampionId}/upvote` toggles a viewer's upvote (`voterToken` hashed with SHA-256) and immediately persists upvoted `youtube_search` candidates to `matchup_videos` as `verified` (`origin: "saved"`).
- UI: two champion pickers on `/`, fixed selected-champion slots, blue theme for the player's side, red theme for the opponent, and a center `WinTop!!` button enabled once both champions are selected.
- Clicking `WinTop!!` navigates to `/matchup/{playerChampionId}/{opponentChampionId}` (`SCR-003` / `match_up`), which renders a compact header, a video selector bar (with `+ YouTube候補を検索` on-demand button), a first-view-fitted 16:9 YouTube embed player, an upvote toggle button (`👍 参考になった`), external watch link (`target="_blank" rel="noopener noreferrer"`), provenance metadata, empty state (`この対面の確認済み動画はまだありません。`), and explicit error alerts.
- Riot Data Dragon attribution and the Riot non-endorsement notice are shown in the UI.
- Phase 2A (implemented): `backend/src/app/video_analysis.py` parses YouTube video descriptions for runes (full 9 slots), summoner spells, and timeline timestamps (kill events flagged); `backend/src/app/data/game_assets.json` (generated by `scripts/update_game_assets_catalog.py`, Data Dragon 16.22.1, rune `aliases` for legacy names) is served at `GET /api/v1/game-assets`; metadata is stored in `matchup_video_metadata`; endpoints `POST /api/v1/matchups/{p}/{o}/analyze` and `PUT /api/v1/matchups/{p}/{o}/metadata`; UI panel `frontend/src/components/VideoMetadataPanel.tsx` (rune tree, spells/items, click-to-seek timeline, manual editor).
- Optional env `YOUTUBE_API_KEY` switches candidate search to YouTube Data API v3; otherwise YouTube HTML is parsed.

## Data-source decisions

- Use Riot Data Dragon for champion IDs, localized names, and icons. Keep patch/version and source provenance; review catalog changes before adopting a new patch.
- Phase 1 replay candidates are manually reviewed YouTube watch-page links. Do not download, mirror, crop, independently host thumbnails, or redistribute videos.
- Before public release, register the player-facing product in Riot Developer Portal and verify current Riot policies and required visible notice. No policy compliance or approval is guaranteed by this handoff.
- `phase1-source-research.md` contains a longer research note but is intentionally Git-ignored. The decisions needed for development are summarized here; recheck current official terms before release or API automation.

## YouTube data retention

Everything fetched from the YouTube API (video title/channel/URL rows, builds extracted from descriptions, and the votes attached to those rows) is deleted 21 days after `matchup_videos.fetched_at` (hard cap 30, policy III.E.4.c/d; see DEC-016 and DEC-017; the short period also keeps information fresh across game patches). Manual input hangs off the same row and expires with it. No refresh, plain deletion. `app/retention.py` does it (`python -m app.retention`; production runs it from a systemd timer, `deploy/install-retention-timer.sh`) and `_load_saved_matchup_videos` also hides expired rows. Any new code that stores YouTube-derived data must set `fetched_at` and be covered by the purge. Frame/video analysis is NOT allowed without prior written approval from YouTube (see the terms research in the Phase 2B notes).

## Versioning

`VERSION` (repo root) is `0.<phase>.<push number>`: the first number stays `0` until release, the second is the current phase (now `2`), and the third **must be bumped on every push to `main`**. It is shown in the footer (`v0.2.1`, commit in the tooltip) and at `GET /api/version`; `deploy/update.sh` passes it and the commit into the build. Run `./scripts/install-git-hooks.sh` once per clone: its pre-push hook rejects a push to `main` when `VERSION` is unchanged (`--no-verify` to skip). Bump `VERSION` in the same commit as the change, or in a final commit before pushing.
